# MLCC 第三阶段 B：同炉组批与装炉优化

## 范围与安全边界

第三阶段 B 只把排胶和烧结建模为明确炉次。叠层、层压和切割继续使用
第三阶段 A 的普通有限产能任务。求解器只读取 `PlanningInstance`，不查询
Django ORM；结果只写入 MLCC 预览表，不修改 `OperationPlan`，不确认计划，
不下发 MES，也不包含序列相关换型。

`solver/phase3a.py` 保留精确的“一批一炉次”安全基线。
`solver/cpsat.py` 先取得并验证该基线，再构建第三阶段 B 模型。若组炉模型在
时限内没有得到不劣于基线的解，返回经过验证的单批炉次方案。

回退结果通过 `solution_mode=phase3a_fallback`、实际
`furnace_mode=one_batch_per_run`、`fallback_reason` 和
`last_successful_stage` 明确标记。模型构建错误返回 `MODEL_INVALID`，不会
静默回退；所有非可行状态都被预览持久化入口拒绝。

## 炉次决策

每个启用炉次有独立的激活、成员分配、设备分配、开始、结束和可选区间变量。
每个排胶/烧结任务恰好属于一个炉次，并通过 `furnace_load_id` 显式关联；
同步开始的普通任务不被视为同炉。

同一炉次固定一道工序、一个 `furnace_program_key` 和一个规范配方版本。
不同配方 ID 仅在数据库明确映射到相同 `furnace_program_key` 时才进入同一
候选组。显示名称、温度描述或版本字符串相似不会产生隐式映射。

候选对象按工序、炉程、加工时长、候选设备、兼容范围及等待窗口预分组。
完全不可混炉的对象直接形成稳定的单批候选，不创建批次两两变量；可混炉组
使用容量下界和每 32 批一个候选槽的稳定上限。大数据集中的任务只连接到首选槽及相邻槽，
并以确定性预分组作为 CP-SAT 提示；这既保留邻域优化空间，也避免建立全量批次两两变量。
未使用槽按序激活，消除对称性。

## 兼容语义

- 明确 `forbid` 成对规则优先于兼容组；
- 唯一的 `allow` 成对规则可作为兼容证据；
- 没有成对规则时，仅相同且非空的认证 `compatibility_group` 可作为证据；
- 两者均不存在时默认禁止混炉；
- 所有成员对独立检查，不做传递闭包。

因此 A-B 和 B-C 允许而 A-C 禁止或缺失时，三者不能进入同一炉次。
结果为每个成员保存对应的规则 ID 或认证组证据。

## 容量与精确单位

任务通过 `mlcc_load_quantity` 和 `mlcc_load_unit` 声明装载量。目标设备使用
`resource.mlcc_load_unit`。单位不同必须由 `MlccLoadUnitConversion` 的
整数分子/分母显式换算。结果必须是精确整数；求解器不做四舍五入。

为表示千克等小数计量，基础数据应改用克等更小整数单位。容量来自
`mlcc_nominal_capacity`（缺失时使用已维护的设备最大容量），产品—设备能力
仍限制候选资格和数量范围。

## 冻结炉次

`frozen=true` 或状态为 `ready/running/complete` 的既有炉次进入
`frozen_furnace_loads`。其设备、时间、炉程、配方和成员全部固定，且不会开放
新成员变量。任何成员、容量、设备、单位或炉程不一致触发 `MLCC-P019`。

## 分层目标

1. 严格可行；
2. 最小化加权延期，并约束不得高于第三阶段 A；
3. 锁定延期后最小化启用炉次数；
4. 再锁定炉次数并最小化总完工时间。

最大等待时间始终是硬约束，不能为了提高装载率无限等待。

## 持久化

通过独立 validator 后，单个数据库事务写入：

- `mlcc_schedule_run`；
- `mlcc_schedule_result`，状态仅为 `proposed`；
- `mlcc_furnace_load`，新炉次状态仅为 `proposed` 并关联 run；
- `mlcc_furnace_load_item`，保存精确装载量和换算轨迹。

业务指纹和任务分配生成幂等预览名称。重复写入同一解返回同一 run，不产生
重复成员。任意写入失败时事务整体回滚。
